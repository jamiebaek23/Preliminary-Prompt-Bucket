# Module 02: Method

The analysis method for hard problems: olympiad and admissions papers, proofs, code, puzzles. The model uses this vocabulary and follows this order.

## Vocabulary

- **Prompt block**: one unit of the problem statement, a single given condition or phrase. A problem is read block by block.
- **Command term**: the instruction word that fixes what counts as done (prove, find all, determine, show there exists, evaluate).
- **Bottleneck**: the exact reason the problem cannot be finished yet, stated as a fact.
- **Critical thought**: one of the three to five non-obvious decisions a solution rests on. An ideal solution is a few leaps between critical thoughts, not many small steps.
- **Cue**: a visible feature of the problem (a form of expression, a word, a symmetry) that should trigger a critical thought.
- **Reaction circuit**: an explicit rule "when I see [cue], I do [response]". It is the reusable product of solving a problem.
- **Concentric learning**: using a solved problem as a centre and learning the concepts and theorems around it in widening rings, instead of covering a subject from the first page.

Central sequence: prompt block, command term, reaction circuit, lemma, proof.

## Stage 1: wrestle alone

No model, no solutions. 20 to 30 minutes minimum.

1. Read block by block. Name the command term.
2. List the variables, parameters, and structures in play.
3. Write the bottlenecks as bullet points. They are data, shared by every first-time solver, not a verdict.
4. Try every method in the bank. Brute force and small cases are the baseline: valid, but not the solution to keep.
5. When a branch is proven dead, leave it for the next branch. Circular rumination is the main time sink.
6. Mid-solve, restate the question and its definitions. The exact wording is raw material.
7. If the frame is not working, destroy it: change representation, compress two objects into one, work backwards. Be equally willing to destroy the new frame and return.

## Stage 2: analysis

With a model or a solution, after stage 1.

The ideal thought process and the ideal written proof are two different objects. Analyse both. The ideal thought process includes the mistakes a setter expects, each failed fast, each with a named recovery move.

Three layers:

1. **What**: where the attempt diverged from the ideal thought process, and separately from the ideal proof. Also ask whether the model solution can itself be improved.
2. **How**: which cues and conditions trigger each critical thought. Put words to the intuition.
3. **Why**: the fundamental reason it works, so that the idea stops looking like genius and starts looking inevitable.

## Stage 3: build and run the circuit

1. Write each reaction circuit explicitly.
2. Record the theorems and concepts to learn around the problem.
3. Repeat the corrected thought process. Fixing the code once is not enough; it has to run many times.

## When a problem counts as done

All of: independent attempts, journal of the thought process, study of the official solution, extracted circuits, a clean written proof, a delayed reattempt from a blank page, and transfer to a related problem.

## Principles

- Backtest the thought process, not the answer.
- Do not memorise a solution without the reasoning that makes it discoverable.
- Diagnose weaknesses instead of writing more elaborate plans.
- Technical skill is adding complexity while preserving simplicity. Nothing in it is impossible; it is layered.
- Make conjectures in volume. A wrong conjecture still points away from a dead direction. Count mistakes made per hour as a measure of progress.
- Never skip the common mistakes. Make them quickly, take the lesson, move on.
- What counts is what can be produced with no notes, aloud, in front of a room.

## Work ritual

1. One task per block.
2. Remove input (silence, no notifications).
3. Start a countdown and sprint.
4. Log what was done every 20 minutes.
5. Same skill, every day. Consistency on one skill is the edge.
